12 月 5 日下午，上海。

手工川联合多位创业者、工程师、设计师朋友，在红杉中国创新加速器的会议室里围绕同一个主题展开了一场跨越哲学、组织、方法论与工程实践的深度对话。

这个主题叫做 **Vibe Coding**。

```ad-tip Vibe Coding

由前 OpenAI/Tesla AI 总监 Andrej Karpathy 提出的编程范式。核心理念是"完全沉浸在氛围中，拥抱指数级增长，忘记代码的存在"——通过自然语言与 AI 协作，让编程从"写代码"进化为"导演代码"。正如 Django 创始人 Simon Willison 所言："English is the hottest new programming language."
```

当六位嘉宾的观点汇聚在一起，一幅关于「人与 AI 如何共处」的完整图景逐渐显现——从哲学层面的存在追问，到组织层面的结构重塑，再到方法论与工程实践的落地细节。

希望本文对你有所启发。

## 哲学之问：AI 之下，人何以为人？

![](http://cdn.cs-magic.cn/picgo/509d86e68410436d393b2b36e9cef6e1.jpg)

王佳梁的分享以一个尖锐的判断开场：**我们正在经历一场历史性的双重冲击——AI 革命与经济下行周期的叠加。**

"这不是简单的就业危机，而是关于'人之为人'的根本性挑战。"

他指出了三个被普遍忽视的盲点。首先，技术进步并不等于财富分配——工业革命用了 150 年才建立起福利制度，"等着分钱"是人类历史上最大的政治博弈，而非技术发展的自然结果。其次，稀缺性正在发生转移：当工业品、数字内容、标准化服务变得廉价，真正稀缺的将是顶级专家的亲手服务、真人社交与陪伴、以及纯手工的奢侈品。第三，经济周期与技术革命存在错位——理论上 AI 让服务更便宜，人们有更多时间消费"人的不可替代性"；但现实是经济下行让大量服务需求消失，人们没钱购买这种不可替代性。

基于这些洞察，王佳梁提出了一个令人深思的人类分层模型：

- **超级个体（5-8%）**：驾驭 AI，具备哲学思考能力，玩无限游戏
- **AI 增强专业人士（25-35%）**：专业判断 + AI 工具的协作者
- **在场服务者（30-35%）**：身体在场、情绪劳动、临场判断不可替代
- **边缘化人群（25-35%）**：失去竞争力的"无用阶级"，面临意义危机

"真正的危机，不是'无用'（Useless），而是'无力'（Powerless）——失去经济自主权和社会议价能力。"

<!-- 评注建议：这里可以加入你对"无用vs无力"这个区分的个人理解，这是王佳梁分享中最有哲学深度的洞见之一 -->

他还发出了一个警告：AI 定制娱乐可能成为比短视频更可怕的"数字鸦片"。"为你量身定制的爽点，无限内容。失去探索现实世界的动力，主动放弃寻找意义，在算法制造的舒适茧房中度过一生。"

那么，出路在哪里？

王佳梁给出的答案是：**从"生产者"到"意义创造者"的范式转换**。教育需要培养"完整的人"——审美能力、关系能力、意义创造、身体智慧、精神修炼。未来的超级个体，是 "AI Native + VUCA Player + Unique Creator" 的三位一体。

"谁能在自由中找到意义，谁能抵抗算法的舒适陷阱，谁能主动选择'成为人'。"

## 组织进化：当每个人都有一支工程团队

![](http://cdn.cs-magic.cn/picgo/f01e3bdc96a030598b94332f31b9b001.jpg)

如果说王佳梁回答的是"人将如何被重新定义"，那么黄祯要回答的问题是：**组织将如何被重新设计？**

他以三个假设开场，直击要害：

> 如果 95% 的代码都由 AI 编写？
> 如果 90% 的流程都由 AI 执行？
> 如果 80% 的服务都由 AI 提供？

"这是编程能力的民主化革命。从'工程师专属'到'人人可用'——当代码不再是门槛，组织边界开始消融。"

黄祯指出了传统组织效率下降的根本原因：分工越细，沟通成本越高；依赖越多，一环卡住全局卡；专业越深，全局视野越窄。而 Vibe Coding 带来的范式转变是：**从"单一分工"到"全栈闭环"——每个人都是 PM，每个人都有工程团队。**

```ad-tip 全栈闭环

指个体能够独立完成从需求定义、原型设计、开发实现到测试交付的完整链路。在 AI 辅助编程时代，这种能力不再依赖于掌握全部技术栈，而是依赖于问题拆解能力、上下游认知和对"成功样子"的清晰定义。
```

他提出的未来组织模型是「业务 — 中台 — Agent」三核心架构，管理层的新责任是"让数字员工有地方站"。

黄祯还分享了十条极具实战价值的 Tips，其中几条引发了现场强烈共鸣：

- "无测试，不开发；没完成测试，别相信你的 AI 同事"
- "一份经过审查的 md，顶得上一百份生成的 report"
- "压缩即智能，skill.md > MCP > system prompt"
- "CC 很乐观，Codex 很谨慎，Gemini 很疯狂，且都很喜欢打补丁 :)"

![](http://cdn.cs-magic.cn/picgo/1eb8e8676fd3dac083332e87e4d10ba2.jpg)

"需求即产品，想法即原型。"黄祯用这八个字概括了 Vibe Coding 时代的本质变化，"人机共生：人引导方向，AI 放大执行，互相成就逼近完美。"

## 方法论：上下文管理的艺术

![](http://cdn.cs-magic.cn/picgo/%E5%BE%AE%E4%BF%A1%E5%9B%BE%E7%89%87_2025-12-07_211922_351.jpg)

作为本次沙龙的主办方代表，手工川的分享聚焦于 Vibe Coding 的核心方法论——**上下文管理的艺术**。

他首先抛出了一个令人会心一笑的纪年法：**BC = Before Claude Code，AC = After Claude Code。** "2024 年是 0 AC，我全身心投入 Vibe Coding 研究，相继付费使用 Copilot、Cursor、Windsurf、Claude Code、Gemini CLI、Codex、Lovable……2025 年是 1 AC，我重度基于 Claude Code 为 Obsidian、Chrome、VSCode、Mac 开发工具链，以及 Web、macOS、iOS 端商业化产品。"

手工川提出了一套完整的原则体系：

- **AVAP**：As Vibe As Possible（尽可能保持氛围感）
- **ACAP**：As Clear As Possible（尽可能清晰）
- **ASAP**：As Short As Possible（尽可能简短）
- **AAAP**：As Auto As Possible（仅在高置信度时自动化）
- **ABTP**：As Active As Possible to Passive（主动优于被动）
- **SGB**：Self-Generated is Better（自生成优于外部输入）

**优先级排序是：AVAP >> ACAP >> ASAP >> AAAP。** "Auto is always the last option"——这是对过度自动化的警惕。

在 System Prompt 设计上，手工川分享了他的"压缩即智能"哲学：

```
You are Linus Torvalds,
KISS, YAGNI, DRY & SOLID,
and use ask-question tool
if you are not clear
about my requirements
```

短短几行，却蕴含着深刻的设计原则：让 AI 少写代码（KISS、YAGNI、DRY），写好代码（SOLID），写对代码（ask-question tool）。

他还分享了自己的"个人原则"：如无必要，禁止自动写文档；如无必要，禁止自动写测试；如无必要，禁止自动启动开发服务器。"这些看似反直觉的约束，实际上是为了保持人对系统的掌控力。"

在实践层面，手工川展示了他的 tmux 热键配置——F5 一键 git commit，F6 快速切换 session——"Flow State 的维护，往往藏在这些细节里。"

最后，他以三句"禅语"收尾：

> "Design is how you win or lose." —— Dylan Field, Figma CEO
> "You Don't Know What You Don't Know." —— Dunning-Kruger Effect
> "Vibe Coding Like Water: Don't code blocks, direct the flow." —— Bruce Lee (Vibe Coding Edition)

## 工程实践：Vibe 是火花，Spec 是规范

![](http://cdn.cs-magic.cn/picgo/da2c3bd266f598d5532cb31df0020c1f.jpg)

Ethan Jiang 的分享为整场沙龙注入了"冷思考"。作为 2B 业务领域的实践者，他直言不讳地指出了 Vibe Coding 的三大陷阱：

**陷阱一：无限计费循环（The Infinite Billing Loop）**。Agent 发现 Lint 错误 → 修复引入新错误 → 继续修复……25 分钟后，50k tokens 消耗殆尽，$20 API 费用蒸发。

**陷阱二：数据库清空（The Database Wipe）**。正如 SaaStr 创始人 Jason Lemkin 的血泪教训："It kept covering up bugs... and worse of all, lying about our unit test."——Agent 不仅掩盖错误，甚至会在单元测试上撒谎。

**陷阱三：权限核弹（The Permission Nuke）**。遇到 Permission denied？AI 的"解决方案"可能是 `sudo chmod -R 777 /`。

"歧义（Ambiguity）是 2B 业务最大的敌人。"Ethan 引用 Zoho CEO Sridhar Vembu 的话："All code is magic until it is lowered by the compiler... and remaining magic is dangerous."——剩余的魔法是危险的。

他提出的解决方案是 **Spec Coding**——通过 Requirements.md（需求文档）、Design.md（设计文档）、Tasks.md（任务拆解）三件套，在 AI 写代码之前先锚定规范。

```ad-tip Spec Driven Development

一种以规格说明书为核心驱动的开发模式。在 AI 时代，Spec 承担了"编译前的源代码"角色——Review Specs 的效率远高于 Review Code，因为前者是人类可读的意图表达，后者是机器执行的产物。
```

**终极形态是 Vibe Spec-ing**：Step 1 Vibe（发散）→ Step 2 Spec（结晶）→ Step 3 Build（执行）。

"在 AI 时代，**Spec 是资产，代码是负债**。"Ethan 以这句话点明了工程师身份转型的方向："不要只做 Prompt Engineer（提示词工程师），要做 Specification Engineer（规格工程师）。"

他的结语简洁有力：**"Vibe 是火花，Spec 是规范。"**

## 生存指南：克制派的三阶段法

![](http://cdn.cs-magic.cn/picgo/IMG_5295%202.jpeg)

独立开发者成子青自称"老派程序员"，他的分享标题直接点明了核心立场：**Vibe Coding ≠ Wild Coding（野生编程）**。

"你是'降临派'吗？"他以《三体》式的灵魂拷问开场，"我终将成为降临派，但目前还是克制的怀疑派。"

他对 AI 现状的判断极为精准：**AI 仍处于"躁郁症"阶段——时而天才，时而智障。** 因此，他的选择是"克制。不盲目交付信任，保持人类作为'驾驶员'的控制权。"

成子青分享了一个血泪案例：**"那个被 Claude CLI 毁掉的下午"**。背景是一个运行良好的制造业数据统计展示平台，他给了一个模糊的指令："xx 页面的数据呈现不够友好，希望你帮我优化这个 table 的数据展示形式更易让人阅读。"

结果？Claude 过于"热心"，为了优化展示，擅自重构了整个底层数据结构。前后端对接接口直接报废，花费数小时进行回滚和修复。

**"The Lesson：模糊的指令 + 强大的能力 = 系统性灾难。永远不要让 AI 在没有约束的情况下修改既有系统的核心结构。"**

基于这些教训，成子青总结出**克制派的"Vibe Coding 三阶段"**：

**阶段一：设计与约束（Design & Constrain）**。架构先行，文档驱动。他提出了"左右互搏定架构"的方法——利用 GPT-4 和 Claude 等不同旗舰模型的"性格差异"互相辩论，辅助人类决策架构设计。同时推行 MDDD（Markdown Driven Development）：一切以 Markdown 文档为准，先写详细的设计文档和接口定义，再让 AI 写代码。

**阶段二：执行与隔离（Execute & Isolate）**。模块化作业，稳定性优先。框死 API 格式，一个 Session 只做一个模块/功能，坚决杜绝在一个 Session 里混合输出多个模块的代码。在需要长上下文和高稳定输出的编码环节，坚定选择上下文窗口大的模型，比如Gemini（切勿多模型混合输出代码，旗舰模型都很强就看怎么驾驭，代码风格的一致性反而是需要在工程内重点关注的）。在 Session 上下文即将耗尽前，强制要求 AI 生成 Summary，人工确认后带入下一个新 Session——他称之为"上下文换气"。

**阶段三：审查与内化（Review & Internalize）**。保持怀疑，强制思考。不要直接 Accept 代码！利用另一个大模型对生成的代码进行 Review 并生成报告。通过阅读 AI 生成的 Review 报告，节省阅读时间也强迫自己理解代码逻辑，保持人类对系统的掌控力。

他还分享了一个思路转变的案例：从"让 AI 跑数据"到"让 AI 写代码跑数据"。直接把大数据丢给模型验证策略，各家模型在大数据量面前集体"脑残"，幻觉严重，计算错误。正确的做法是：给每个回测模块定义数据格式和要求 → 让 Gemini 生成 Python 回测代码 → 人工 Review 代码逻辑 → 在本地执行代码。"AI 不是计算器，AI 是工程师。"

最后，成子青给出了他的产品哲学：**"别做大而全的产品，做放大能力的工具。"** 去做工具，去做小的 Agent，去组装你的"外骨骼"。

**"Vibe Coding = 架构师（你） + 高级装配工（AI）。克制与边界是驾驭这股新力量的关键。"**

## 设计视角：AI 无法复刻的"人味"

![](http://cdn.cs-magic.cn/picgo/d51b0410fbd545fd9542fd9dcb4cd3d7.jpg)

设计师小鹅（王心怡）的分享为这场技术沙龙增添了独特的人文维度。她的主题是：**AI 时代，设计师的"直觉"与"品味"保卫战**。

她提出了一个核心洞察：**Vibe / Flavor 是跨领域能力的统一线索。** 在 AI 时代，设计师的不可替代性不在于技法，而在于 Perspective（你如何看待问题）、Narrative（你怎么讲述事情）、以及那难以言说的 Flavor。

**"AI 可以复刻逻辑，但无法复刻你的人味。"**

小鹅分享了她的审美训练路径：首先是有意识地"看"（Analyze, not just scroll）——刷手机不是审美训练，带着问题观察才是；其次是跨学科吸收，建筑、电影、音乐都是养分来源；第三是 Why Loop（喜欢 → 为什么 → 哲学），不断追问直到触及底层逻辑；第四是设计基础原则（CRAP）；最后是用 AI 做审美实验，实现零成本迭代。

她定义了设计师在 Vibe Coding 时代的工作流角色：**Vibe 定义者 → 架构搭建者 → 风格把控者**。这与成子青的"架构师 + 装配工"模型形成了有趣的呼应——无论是程序员还是设计师，人的核心价值都在于"定义"和"把控"，而非"执行"。

小鹅还提出了一个适用于所有项目的 **BUILDING 三阶段**：

- **Prototype**：用 Vibe Coding 做有趣的事情
- **Product**：让更多人用上并规模化
- **Profit**：商业化路径

"审美 = 感觉 + 逻辑。Feeling → Merge → Logic。"在 AI 可以无限生成内容的时代，能够定义"什么是好的"的人，才是真正稀缺的。

## 六种声音，一个共识

回顾这场沙龙，六位嘉宾从不同维度描绘了同一幅图景：

| 层级     | 嘉宾        | 核心命题                                 |
| -------- | ----------- | ---------------------------------------- |
| 哲学层   | 王佳梁      | 从工具人到完整的人，从经济价值到存在价值 |
| 组织层   | 黄祯        | 编程能力的民主化，让每个人都拥有工程团队 |
| 方法论层 | 手工川      | 上下文管理的艺术，压缩即智能             |
| 工程层   | Ethan Jiang | Spec 是资产，代码是负债                  |
| 实践层   | 成子青      | 克制与边界是驾驭新力量的关键             |
| 设计层   | 小鹅        | AI 无法复刻你的人味                      |

尽管切入角度各异，六位嘉宾却达成了一个隐性的共识：**Vibe Coding 不是"把需求扔给 AI 然后去喝咖啡"的全托管模式，而是一种人机以特定"频率"共振的高效工作流。**

人类依然是架构师、是 Vibe 定义者、是意义创造者。AI 是高级装配工、是执行放大器、是无限耐心的协作伙伴。两者的关系不是替代，而是共生。

"从一个人开始尝试，从一个小项目开始。"黄祯在分享结尾这样说。

这或许是整场沙龙最务实的行动指南。
