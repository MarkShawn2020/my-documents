在上一篇文章 [推荐一个 Mac 神器：重复操作一键自动化](https://mp.weixin.qq.com/s/L65ZFiQJGPUljxmAiXWZzg) 中，我分享了如何基于 Alfred 实现「一键打开无边记 (Freeform) 并自动创建画板」的高效工作流。

然而，在随后的高频使用中，我发现这个 seemingly perfect 的脚本存在由于**修饰键穿透**导致的间歇性失灵。

起初，我将矛头指向 Alfred 的执行稳定性，后又怀疑是 Mac 内置应用 Freeform 的响应问题。但在经过反复调试与排查后，真相终于浮出水面：这并非软件 bug，而是一个典型的自动化交互设计缺陷——我们用于触发工作流的快捷键（`cmd+shift+alt+N`）与后续脚本执行的快捷键（`cmd+N`）发生了物理层面的冲突。

本文将复盘这一问题的排查过程，并提供基于 GUI Scripting、键位策略调整、Alfred 原生功能以及 Hammerspoon 的四种解决方案。

<!-- 评注建议：此处可以简要点出，自动化脚本编写中“人手速度”与“脚本速度”的时间差是新手最容易忽视的坑。 -->

### 问题溯源：修饰键的物理残留

问题的核心在于：当我们按下 `cmd+shift+alt+N` 触发 Alfred 工作流时，手指往往还停留在 `cmd+shift+alt` 这三个修饰键上。此时，脚本紧接着执行 `keystroke "N" using {command down}`。

操作系统接收到的信号并非我们预期的 `cmd+N`，而是物理按键与脚本模拟的叠加状态——`cmd+shift+alt+N`。

![](http://cdn.cs-magic.cn/picgo/20251201055623385.png)

这是 Alfred（以及许多自动化工具）的一个设计特性：默认情况下，触发键的修饰键状态会穿透给后续的工作流。这种机制虽然在某些场景下有用，但在此处直接破坏了我们的原子操作。

![](http://cdn.cs-magic.cn/picgo/20251201060023118.png)

![](http://cdn.cs-magic.cn/picgo/CC%E4%B8%8A%E4%B8%8B%E6%96%87%E6%9C%BA%E5%88%B6-2025-12-01-150320.png)


```ad-tip 修饰键穿透 (Modifier Key Penetration)

在操作系统自动化中，"修饰键穿透"是指用户触发动作时按下的修饰键（如 Command, Shift, Alt/Option）在脚本执行后续模拟按键时仍然处于“按下”状态，从而干扰脚本逻辑的现象。例如，用户按 `Cmd+S` 触发脚本输入 "A"，系统实际接收到的可能是 `Cmd+A`（全选）。
```

借助 CC、Gemini 和 ChatGPT 等 AI 助手，我整理了以下四种不同维度的解决方案。

### 方案一：GUI Scripting (基于 UI 元素的点击)

既然键盘信号存在干扰，最直接的思路是避开键盘模拟，转而通过 Accessibility API 直接点击菜单栏。

![](http://cdn.cs-magic.cn/picgo/20251201060344448.png)

Gemini 在此方案中表现出色，它不仅给出了通过 `click menu item` 绕过按键冲突的代码，还贴心地提供了中英文双语系统的适配方案：

```applescript
	tell process "Freeform"
		try
			-- 方法：直接点击菜单栏，这会忽略你手上按着的 Alt/Shift 键
			-- 请根据你的系统语言选择下面的一行：

			-- 如果是中文系统：
			click menu item "新建看板" of menu "文件" of menu bar 1

			-- 如果是英文系统 (把上面中文的注释掉，启用下面这行)：
			-- click menu item "New Board" of menu "File" of menu bar 1

		on error
			-- 如果找不到菜单，可能是应用没完全加载或语言不对，此时可以尝试回退到模拟按键（虽然可能会失败）
			keystroke "n" using {command down}
		end try
	end tell
```

**优点**：完全无视物理按键状态，稳定性高。
**缺点**：依赖菜单栏层级结构，若软件更新导致菜单名变更需维护代码。

### 方案二：键位策略调整 (Key Combo Strategy)

![](http://cdn.cs-magic.cn/picgo/20251201220555938.png)

```applescript
tell application "Freeform"
    activate
    delay 0.1
    tell application "System Events"
        keystroke "n" using {command down}
    end tell
end tell
```

AI 提出的另一种思路是修改触发快捷键，使其修饰键与目标快捷键（`cmd+N`）保持一致。

例如，我们将触发键设为 `cmd+K`。当我们松开 `K` 但仍按住 `cmd` 时，Alfred 触发脚本发送 `N`，此时系统接收到的就是 `cmd+N`。经实测，此方案可行。

<!-- 评注建议：这里可以补充一点，选择快捷键是一门玄学，既要避免系统冲突，又要符合人体工学，还要好记。 -->

但此方案存在明显的逻辑陷阱：
1.  **记忆成本**：快捷键体系牵一发而动全身，随意更改会破坏肌肉记忆。
2.  **Edge Case**：如果触发键直接设为 `cmd+N`，则会造成死循环或立即冲突。

### 方案三：最佳实践——基于 Alfred 原生 Dispatch Key Combo

![](http://cdn.cs-magic.cn/picgo/20251201220656036.png)

这无疑是最优雅、最符合 Alfred 设计哲学的方案。它完全摒弃了代码，利用 Alfred 内置的封装模块，清晰地构建了一条自动化链路：

1.  **Hotkey**：检测用户按下 `cmd + shift + alt + N`。
2.  **Launch App**：打开或激活 Freeform。
3.  **Delay**：设置 0.2s 延时，**给用户手指松开按键的缓冲时间**。
4.  **Dispatch Key Combo**：由 Alfred 内部接管，发送干净的 `cmd + N` 指令。

值得注意的是，在询问该功能的位置时，AI 们的表现参差不齐。Gemini 提供了准确的路径，而 ChatGPT 给出的指引是错误的。

![](http://cdn.cs-magic.cn/picgo/20251201221253417.png)

**正解**：Alfred 的 `Dispatch Key Combo` 功能位于 **Outputs** 菜单下，而非 Actions。

![](http://cdn.cs-magic.cn/picgo/20251201221312261.png)

### 方案四：降维打击——使用 Hammerspoon

虽然 CC 在本次 factual checking 中表现一般，甚至未将 Key Combo 列为标准答案，但它提出了一个极具极客精神的替代方案：**Hammerspoon**。

![](http://cdn.cs-magic.cn/picgo/20251201221824950.png)

Hammerspoon 是一个基于 Lua 语言的 macOS 自动化神器，它提供了比 Alfred 更底层的系统控制能力。

![](http://cdn.cs-magic.cn/picgo/20251201221928871.png)

其配置方式类似于 PicGo，虽然没有 GUI 工作流那么直观，但通过简单的 Lua 脚本即可实现强大的功能。

![](http://cdn.cs-magic.cn/picgo/20251201222038594.png)

为了保持代码整洁，我建议将配置模块化。例如创建一个 `hotkeys.lua` 专门管理快捷键，并在 `init.lua` 中引用：

![](http://cdn.cs-magic.cn/picgo/20251201222141832.png)

Hammerspoon 的控制台（Console）提供了详尽的日志，非常适合调试复杂的自动化逻辑：

![](http://cdn.cs-magic.cn/picgo/20251201221901761.png)

在发现方案三之前，Hammerspoon 是我最心动的选择。如果你需要更精细的窗口管理或系统级事件监听，Hammerspoon 是不二之选。但对于单纯的模拟按键，Alfred 的原生方案胜在轻量与开箱即用。

此外，读者还推荐了 **Raycast**，这也被视为 Alfred 的强力挑战者，尤其在插件生态上表现亮眼，值得后续深入探索。
