这是一个非常典型的 Rust + TypeScript (通常是 Tauri 或 Electron 架构) 桌面端应用场景。**

在 macOS 上实现通用的滚动截图（截取任意应用程序窗口，而不仅仅是你自己的 Webview），**核心难题不在于 TS 前端，而在于 Rust 后端如何高效地与系统交互和处理图像。**

目前市面上并没有一个单一的、开箱即用的“滚动截图 Rust create”能完美解决所有问题。实现高性能方案通常需要组合几个不同领域的开源库。

以下是基于 macOS + Rust + TS 栈的推荐开源方案组合和架构思路，旨在达到**高性能（快）**和**好效果（准）**。

---

### 核心架构思路

1.  **TypeScript (前端)**：负责用户交互（点击“开始截图”按钮），显示预览，以及最后保存文件。
2.  **Rust (后端)**：核心劳动力。负责：
    *   **自动化控制**：模拟鼠标滚轮或键盘按键。
    *   **屏幕捕获**：高效抓取屏幕帧。
    *   **图像算法**：计算位移并拼接图像（最耗性能的部分）。

---

### 推荐的开源方案组合 (Rust 侧)

为了达到最佳性能，我们需要在 Rust 侧选择最强的库。

#### 方案一：工业级高性能组合（推荐）

这个方案利用了 macOS 最新的原生能力和最成熟的图像处理库，性能和鲁棒性是最好的，但配置稍微复杂一些。

| 组件 | 推荐库 (Crate) | 说明 |
| :--- | :--- | :--- |
| **屏幕捕获** | **`scap`** (或 `xcap`) | **关键推荐**。`scap` 是一个较新的库，它的杀手锏是支持 macOS 的 **ScreenCaptureKit (SCK)**。SCK 是苹果推出的高性能截屏 API，比旧的 CGDisplay 效率高得多，CPU 占用极低，能直接捕获特定窗口或屏幕，非常适合高频截图。 |
| **图像处理/拼接** | **`opencv` (Rust bindings)** | 虽然重，但仍然是王道。OpenCV 的 `matchTemplate` 函数（配合 FFT 加速的 NCC 算法）是计算两张图重叠区域最快、最稳的方法。它还能很好地处理不同色彩空间转换。 |
| **自动化控制** | **`enigo`** | Rust 生态中模拟键盘鼠标输入的标准库。在 macOS 上工作良好，用于发送滚动指令。 |
| **基础图像容器** | **`image`** | Rust 的标准图像库，用于在不同步骤间传递图像数据，或者做最后的裁剪和保存 (PNG/JPG)。 |

**工作流程 (Rust 侧实现):**

1.  **初始化**：前端 TS 通知 Rust 开始，Rust 使用 `scap` 锁定要截图的目标窗口。
2.  **第一次截图**：使用 `scap` 截取当前视口，转换为 OpenCV 的 `Mat` 对象。
3.  **循环**：
    *   使用 `enigo` 向窗口发送“向下滚动”指令（例如滚轮向下滚动固定的 tick 数，或者 PageDown 键）。
    *   *等待短暂时间*（等待 UI 渲染完成，例如 100ms，这是个经验值）。
    *   **第二次截图**：再次使用 `scap` 截图。
    *   **关键算法：计算位移 (Registration)**：
        *   取图 1 底部的一块区域作为模板 (Template)。
        *   调用 OpenCV 的 `cv::match_template` 在图 2 的顶部区域搜索该模板。建议使用 `TM_CCOEFF_NORMED` (归一化相关系数) 方法。
        *   OpenCV 会极快地返回最佳匹配位置的坐标，从而计算出垂直滚动的像素量 ($Ty$)。
    *   **拼接**：根据 $Ty$，裁剪图 2 的新增部分，拼接到大图画布上。
    *   检查结束条件：如果计算出的位移 $Ty$ 接近 0，或者多次尝试都匹配失败，说明到底了。
4.  **完成**：将最终拼接好的大图通过 `image` 库编码为 PNG 数据返回给 TS 前端。

**优点**：
*   **极快**：利用了 macOS 原生 SCK 加速截图和 OpenCV 的 C++ 底层加速匹配。
*   **鲁棒**：NCC 模板匹配算法对轻微的渲染差异有抵抗力。

**缺点**：
*   **构建复杂**：在 Rust 中集成 OpenCV 需要链接 C++ 库，构建环境配置稍麻烦（需要安装 LLVM 和 OpenCV 本身，虽然 `opencv-rust` crate 试图简化这一点）。

#### 方案二：纯 Rust 方案 (替代方案)

如果你不想引入 OpenCV 这种庞然大物，希望保持纯 Rust 技术栈，可以退而求其次。

| 组件 | 推荐库 (Crate) | 说明 |
| :--- | :--- | :--- |
| **屏幕捕获** | **`xcap`** / `screenshots` | 跨平台的截图库，纯 Rust 实现或包装较好的原生 API。 |
| **图像处理/拼接** | **`image` + 手写算法** | 不使用 OpenCV。你需要基于 `image` 库提供的像素访问能力，手写一个滑动窗口匹配算法（比如 SSD - 平方差和）。为了性能，可能需要手写 SIMD 指令加速，或者寻找实现了 FFT 的纯 Rust 库（如 `rustfft`）来实现快速互相关。 |
| **自动化控制** | **`enigo`** | 同上。 |

**优点**：构建简单，依赖纯粹。
**缺点**：性能瓶颈在于图像匹配算法。手写一个比肩 OpenCV 优化过的 FFT 匹配算法非常有挑战性。如果只用简单的像素逐行对比，速度慢且容易出错。

### 必须注意的 macOS 特有“坑”

在 Mac 上做这个功能，算法反而是其次，以下工程问题处理不好，体验会很差：

1.  **Retina 屏幕与 DPI 缩放（重中之重）**：
    *   macOS 的逻辑分辨率和物理像素分辨率通常是 2 倍关系（Retina）。
    *   `enigo` 滚动的距离通常是逻辑像素，而截图库拿到的可能是物理像素。
    *   **解决方案**：在计算拼接和裁剪时，务必搞清楚你拿到的图像数据是 1x 还是 2x 的。通常需要获取当前屏幕的 `scale_factor` 并参与计算，否则拼接出来会错位或大小不一。

2.  **权限问题 (Screen Recording Permission)**：
    *   你的应用必须获得 macOS 的“屏幕录制”权限才能截取其他窗口。
    *   在开发阶段和分发阶段，都要确保正确引导用户授予权限，否则截出来全是壁纸或黑屏。

3.  **固定元素的处理 (Sticky Headers/Footers)**：
    *   如上一个回答所述，macOS 很多应用也有固定的顶部栏。
    *   **工程实践**：在进行 OpenCV 匹配之前，经验性地裁掉截图顶部（例如 100px）和底部的一部分区域，只用中间内容区去匹配，能显著提高成功率。

4.  **滚动惯性**：
    *   macOS 的触控板滚动带有强大的惯性。程序模拟滚动时，最好模拟鼠标滚轮的离散步进，而不是模拟触控手势，否则很难控制滚动的停止位置，导致图像模糊或错过内容。

### 总结

在 macOS + Rust + TS 环境下，实现高性能滚动截图的最佳实践是：

采用 **Tauri** (作为框架) + **Rust** (作为后端核心)。
Rust 后端使用 **`scap`** (利用 ScreenCaptureKit) 进行高效截图，配合 **`opencv` Rust bindings** 进行快速准确的 FFT 模板匹配和拼接，使用 **`enigo`** 进行滚动控制。

这条路径虽然前期在 Rust 中配置 OpenCV 稍麻烦，但一旦跑通，所能提供的性能和稳定性是纯 JS 方案或纯 Rust 简单实现无法比拟的。
